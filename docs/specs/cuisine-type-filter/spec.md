# 음식 종류 필터

## User-visible outcome

이동시간순 음식점 목록에서, 실제로 목록에 있는 음식 종류들 중 하나를 골라 그 종류의 음식점만 볼 수 있다. 필터를 바꾸거나 초기화해도 이미 선택(체크)해둔 곳은 그대로 유지된다.

## Scope

- 이동시간순 음식점 목록 위에 음식 종류 필터를 둔다.
- 필터 선택지는 현재 불러온 목록 안에 실제로 있는 음식 종류들로만 구성된다 (목록에 없는 종류는 선택지에 나타나지 않는다).
- "전체" 선택지를 포함해, 필터를 해제하면 다시 전체 목록이 보인다.
- 필터는 이미 불러온 목록 안에서만 좁혀 보여주며, 서버에 새로 검색을 요청하지 않는다.
- 새로운 위치를 검색하거나 이동수단을 바꿔 목록이 다시 불러와지면, 필터는 "전체"로 초기화된다.

## Out of scope (off-limits)

- 가격대 필터 — [restaurant-data-source](../../decisions/restaurant-data-source.md) 결정에 따라 Geoapify에 가격대 데이터가 없어 이번 범위에서 다루지 않는다.
- 음식 종류별로 서버에 다시 검색을 요청하는 것 — 이미 불러온 20곳 안에서만 필터링한다. 상위 20곳에 없는 음식 종류를 선택해도 새로 찾아오지 않는다.
- 여러 음식 종류를 동시에 선택하는 다중 필터.
- 음식 종류 정보를 리스트 정렬 기준(이동시간순)에 반영하거나 바꾸는 것.

## Acceptance criteria

- 음식점 목록이 나타나면, 그 목록에 실제로 있는 음식 종류들이 필터 선택지로 나타난다.
- 목록에 없는 음식 종류는 필터 선택지에 나타나지 않는다.
- 음식 종류 하나를 선택하면, 그 종류에 해당하는 음식점만 보인다.
- "전체"를 선택하면 다시 모든 음식점이 보인다.
- 필터를 적용한 상태에서도, 필터에 가려진 음식점을 포함해 이미 선택(체크)해둔 곳의 선택 상태와 날짜별 배분 결과는 그대로 유지된다.
- 새로운 위치를 검색하거나 이동수단을 바꿔 음식점 목록이 다시 불러와지면, 필터는 "전체" 상태로 돌아간다.
- 실제 서비스 지역에서 동작을 실행했을 때, 필터 선택지가 실제 목록의 음식 종류와 일치하는지, 필터 적용 결과가 그럴듯한지 눈으로 확인할 수 있다.

## Settled constraints and rationale

- 음식 종류 필터는 Geoapify Places API가 이미 제공하는 세부 카테고리 데이터를 그대로 활용한다 — [restaurant-data-source](../../decisions/restaurant-data-source.md)에서 확인·기록함.
- 필터는 서버 재검색 없이 이미 불러온 목록 안에서만 동작한다 — 구현 범위를 좁게 유지하기로 사용자가 확인함. 그 결과 상위 20곳 밖의 음식 종류는 선택해도 결과가 없을 수 있다는 것을 감수한다.
- 가격대 필터는 데이터 소스 자체가 없어 이번 범위에서 제외한다.

## Assumptions

- 음식 종류 이름은 Geoapify 카테고리 코드(예: catering.restaurant.italian)를 사람이 읽기 쉬운 이름으로 변환해 보여준다. 매핑이 없는 코드는 코드 자체를 보기 좋게 변환해 표시한다.
- 특정 음식 종류로 분류되지 않은(일반 catering.restaurant만 있는) 곳은 "기타" 필터로 묶어서 보여준다 — 개별 필터 개수를 다 더하면 전체 개수와 맞아야 한다는 것을 사용자가 실제로 확인하고 확정함.

## Deferred points

- 가격대 필터.
- 여러 음식 종류를 동시에 선택하는 기능.
- 상위 20곳 밖에서 음식 종류로 다시 검색하는 기능.

## Remaining risks

- 필터가 "이미 불러온 20곳 안"으로 제한되므로, 사용자가 기대하는 음식 종류가 상위 20곳 안에 없으면 필터 선택지 자체에 나타나지 않아 "그 종류가 아예 없다"고 오해할 수 있다.
- Geoapify 카테고리 코드 → 사람이 읽는 이름 매핑이 모든 세부 카테고리를 다 다루지 못할 수 있어, 일부 음식 종류는 코드 형태 그대로에 가깝게 보일 수 있다.
