# 01 — 여행 일수에 따른 날짜별 자동 배분과 경로 추천

## Outcome

사용자가 여행 일수를 입력하면 선택 가능한 맛집 개수 상한이 "일수 × 4"로 늘어나고, 선택한 곳들이 지리적으로 가까운 곳끼리 묶여 날짜별(하루 최대 4곳)로 자동 배분되며, 각 날짜마다 출발점 기준 왕복 방문 순서·구간별 이동시간·왕복 총 이동시간이 나타난다.

## Blockers

None. (선행 스펙 [selected-restaurants-round-trip](../../selected-restaurants-round-trip/spec.md)의 태스크 01이 이미 completed 상태이며, 이 태스크는 그 화면 위에 이어서 구현한다.)

## Acceptance criteria

- [x] 여행 일수를 입력할 수 있고, 그에 따라 선택 가능한 최대 개수(일수 × 4)를 사용자가 알 수 있다.
- [x] 상한을 넘는 선택은 막힌다.
- [x] 아무것도 선택하지 않으면 날짜별 배분 결과가 나타나지 않는다.
- [x] 1곳 이상 선택하면 날짜별 배분 결과가 나타난다.
- [x] 배분된 곳은 지리적으로 가까운 것끼리 우선 묶이며, 어떤 날짜도 4곳을 넘지 않는다.
- [x] 각 날짜마다 출발점 기준 왕복 방문 순서, 구간별 이동시간, 왕복 총 이동시간이 표시된다.
- [x] 선택된 곳이 일수 × 4보다 적어서 일부 날짜에 배정될 곳이 없을 수 있고, 그 경우 해당 날짜에 배정된 곳이 없다는 것을 사용자가 알 수 있다.
- [x] 선택 내용이나 여행 일수를 바꾸면 배분과 각 날짜의 경로가 다시 계산된다.

## Constraints

None.

## Verification

- 서로 다른 대륙의 도시(예: 서울, 파리)에서 2~3일, 6곳 이상을 선택해 실제로 날짜별 배분과 각 날짜의 방문 순서·이동시간을 확인하고, 배분된 묶음이 지리적으로 그럴듯하게 가까운지 눈으로 확인한다.
- 선택 개수가 일수 × 4보다 적을 때 일부 날짜가 비는 경우를 확인한다.
- 상한(일수 × 4)을 넘는 선택을 시도했을 때 막히는 것을 확인한다.
- 여행 일수를 바꿨을 때 상한과 배분이 다시 계산되는 것을 확인한다.
- `npm run typecheck`, `npm run lint`, `npm run test`가 통과한다.

## Execution

- Verification: 지리적 클러스터링(`lib/day-planner.ts`)은 TDD로 먼저 테스트 작성 후 구현 (멀리 떨어진 두 무리가 섞이지 않는지 대조하는 테스트 포함, `npm run test`에서 6개 모두 통과). 왕복 경로 계산 로직은 `lib/route-plan.ts`로 추출해 `/api/route-plan`과 새 `/api/day-plans`가 공유하도록 리팩터링 (이전 스프린트에서 기록된 "최대 개수 상수 중복" 리뷰 발견 사항도 함께 해소됨). `npm run typecheck`/`lint`/`test` 모두 통과. 실제 브라우저에서 파리 기준 여행 일수 2, 6곳 선택 → 1일차 2곳/2일차 4곳으로 지리적으로 묶여 배분되고 각 날짜의 왕복 순서·구간별 시간·총 시간 확인. 8곳(일수2×4)까지 선택 확인, 9번째 선택 시도 시 체크박스가 disabled로 막히는 것 확인. 여행 일수를 2→1로 줄였을 때 선택이 8→4로 잘리고 2일차 섹션이 사라지는 것 확인. tripDays=1, 4곳 선택 상태에서 왕복 결과가 정상 표시되는 것으로 [selected-restaurants-round-trip 태스크 01](../../selected-restaurants-round-trip/tasks/01-selected-restaurants-round-trip.md)의 인수 기준이 새 흐름(`/api/day-plans`)을 통해서도 여전히 충족됨을 재확인. 리팩터링된 `/api/route-plan`도 `curl`로 직접 호출해 정상 동작 재확인.
